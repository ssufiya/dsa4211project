# Bayesian optimisation vs CMA-ES under low effective dimension

Does the performance of Bayesian optimisation (BO) and CMA-ES depend on the
**ambient dimension** $D$, on the **effective dimension** $d_e$, or on whether the
low-dimensional structure is **aligned with the coordinate axes**?

We investigate whether the differences can be explained by each method's
invariance to rotations and by what it has to learn from data:

| Method | Rotation-invariant? | Has to learn | Expected weakness |
|---|---|---|---|
| CMA-ES | yes, up to the box constraint | full $D \times D$ covariance | slow adaptation in high $D$ |
| GP-BO, ARD kernel | no | one lengthscale per input | rotated structure |
| GP-BO, isotropic kernel | yes, up to the box constraint | one shared lengthscale | high $D$ (no input can be switched off) |
| TuRBO-1 (trust-region BO) | no: its trust region is an axis-aligned box shaped by ARD lengthscales | local GP and trust-region size | rotated structure; slow trust-region adaptation when $D$ is large |
| Random search | not applicable (ignores structure) | nothing | baseline |

Authors: see [authors.md](authors.md). Report: [report/report.tex](report/report.tex)
(compiled: [report/report.pdf](report/report.pdf)).

## Environment

Python 3.10 or newer. All dependencies are on PyPI and run on CPU only.

```bash
python3 -m venv .venv                # Windows: python -m venv .venv
source .venv/bin/activate            # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

All commands below assume the virtual environment is active (the prompt starts
with `(.venv)`), in which case `python` works on every platform.

`requirements.txt` lists the minimum versions of the packages the code uses.
The reported results were produced on an Apple Silicon Mac (macOS, arm64) with
Python 3.12.2 and NumPy 2.5.4; each `results/<exp>/environment.json` records the
Python version, platform and NumPy version used for that experiment.

## Data

There is no external data. All test problems are synthetic and generated from a
seed in `code/problems.py`. Every problem has the form

$$f(x) = g\left(A^\top x - z^\star\right) + \varepsilon \left\lVert (I - AA^\top)(x - x^\star) \right\rVert^2, \qquad x \in [-1, 1]^D,$$

where $A$ is a $D \times d_e$ matrix with orthonormal columns and $g$ is a base
function (Ackley or Rosenbrock) with minimum value $0$. In the **aligned** case
$A$ selects $d_e$ coordinates; in the **rotated** case $A$ has random orthonormal
columns. The optimum $x^\star$ is drawn uniformly from $[-0.5, 0.5]^D$ and
$z^\star = A^\top x^\star$, so the minimum value is $f(x^\star) = 0$ and $f(x)$
equals the simple regret. The parameter $\varepsilon$ is $0$ except in the
`followup_approx_lowdim` experiment.

For a given (base function, $D$, $d_e$, alignment, seed), every method sees the
identical problem instance and the identical initial design, so comparisons
between methods are paired.

## Reproducing the results

Each command writes to `results/<experiment name>/` and skips runs that already
exist, so an interrupted run can be resumed by repeating the command.

```bash
# 0. Smoke test (under a minute): checks that the pipeline runs end to end.
#    Its results are not used in the report.
python code/run_experiments.py --config configs/smoke.yaml --workers 2
python code/analyse.py --exp smoke

# 1. Pilot
python code/run_experiments.py --config configs/pilot.yaml --workers 4
python code/analyse.py --exp pilot

# 2. Main experiments
# How do the ambient dimension D and rotation affect each method?
python code/run_experiments.py --config configs/main_dimension.yaml --workers 4
python code/analyse.py --exp main_dimension
# What happens as the number of important directions d_e grows?
python code/run_experiments.py --config configs/main_effective_dim.yaml --workers 4
python code/analyse.py --exp main_effective_dim

# 3. Follow-ups
# What if the "irrelevant" directions matter slightly (eps > 0)?
python code/run_experiments.py --config configs/followup_approx_lowdim.yaml --workers 4
python code/analyse.py --exp followup_approx_lowdim
# Does CMA-ES catch up with a much larger budget (3000 evaluations)?
python code/run_experiments.py --config configs/followup_cmaes_long.yaml --workers 4
python code/analyse.py --exp followup_cmaes_long

# 4. Follow-up investigations (numbers quoted in Section 5 of the report)
python code/investigate.py

# 5. Report
cd report && pdflatex report && bibtex report && pdflatex report && pdflatex report
```

Use `--dry-run` to list the runs a config will perform without running them.
`analyse.py` and `investigate.py` only read saved results and take a few seconds,
so figures and tables can be regenerated without re-running any experiment.

**Runtime.** Measured on the Apple Silicon Mac above with `--workers 4`:

| Experiment | Runs | Elapsed time | Total compute time |
|---|---|---|---|
| `main_dimension` | 900 | about 10.5 hours | about 35 CPU-hours |
| `main_effective_dim` | 600 | about 1.5 hours | about 6 CPU-hours |
| `followup_approx_lowdim` | 240 | about 3 hours | about 4 CPU-hours |
| `followup_cmaes_long` | 360 | under a minute | about 1 CPU-minute |
| `pilot` | 200 | about 15 minutes | about 1 CPU-hour |

CMA-ES and random search take well under a second per run. GP-based methods
dominate: their cost grows with the number of evaluations (GP fitting is cubic in
the number of points) and with $D$ (ARD has $D + 2$ kernel hyperparameters).
Run the main experiments overnight, with as many workers as you have CPU cores.

## What each output means

* Performance measure: **simple regret** $f(x_\text{best})$ of the best point
  evaluated so far, reported as $\log_{10}$ (a difference of 1 means a factor of
  10). Every problem has minimum value $0$, so $f$ itself is the regret. There is
  no observation noise, so the best observed value is also the true value.
* Budget: number of **objective evaluations**, including the `n_init` initial
  points. Wall-clock time is recorded separately (`wall_time_s`, and for GP
  methods `gp_fit_time_s` and `acq_time_s`).
* Figures per experiment, in `report/figures/`: `_convergence`, `_final_vs_D`,
  `_ecdf`, `_walltime`, and `_rotation_effect` (rotated minus aligned median
  $\log_{10}$ regret with 95% CI; the right axis shows the same values as a ratio).
* `summary_final_regret.csv`: median and interquartile range of $\log_{10}$ final
  regret per setting.
* `summary_vs_reference.csv`: paired per-seed difference in $\log_{10}$ final
  regret against CMA-ES, with bootstrap 95% CI and the fraction of seeds where the
  method beat CMA-ES.
* `summary_rotation_effect.csv`: rotated minus aligned median $\log_{10}$ final
  regret per method (unpaired bootstrap 95% CI).
* `summary_diagnostics.csv`: mechanism diagnostics.
  * CMA-ES: `relevant_variance_fraction` $= \mathrm{tr}(A^\top C A) / \mathrm{tr}(C)$
    of the final search covariance $C$ (value for a round distribution: $d_e / D$),
    and `condition_number` of $C$.
  * GP-BO (ARD) and TuRBO on aligned problems: `relevant_recovered_frac`, the
    fraction of the $d_e$ shortest lengthscales that are truly relevant inputs.
  * TuRBO: `restarts`, `n_expands`, `n_shrinks` and `final_length` describe how
    the trust region evolved; the full `length_history` is in each run's JSON.

## Implementation notes and known limitations

* GP-BO uses scikit-learn's `GaussianProcessRegressor` (Matérn-5/2 kernel,
  outputs normalised, hyperparameters by marginal likelihood with restarts) and
  log Expected Improvement. The acquisition is maximised over a candidate set
  (uniform points plus perturbations of the best points), not by gradient-based
  multi-start optimisation as in BoTorch. This favours simplicity and
  transparency over raw performance.
* `refit_every: k` refits kernel hyperparameters every $k$ iterations (the GP is
  still conditioned on all data every iteration) to keep $D = 100$ affordable.
* CMA-ES uses pycma's default population size and `BoundTransform` boundary
  handling, starts from the best initial point with `sigma0 = 0.5` (a quarter of
  the box width), and restarts from a random point if a stopping criterion fires.
* TuRBO-1 follows Section 3 of Eriksson et al. (2019) with the paper's default
  settings (unit-cube side lengths $0.8$ initial, $2^{-7}$ minimum, $1.6$ maximum;
  success tolerance 3; failure tolerance $\max(4, D)$; restart with a fresh random
  design when the trust region collapses). One deviation: Thompson samples are
  drawn exactly over at most 2000 candidates instead of the paper's up to 5000
  with a scalable approximation.
